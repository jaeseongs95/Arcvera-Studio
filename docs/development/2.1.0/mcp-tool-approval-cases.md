## D-0089 numeric review ceiling — plan before fixtures

The uncommitted D-0087 candidate allowed every finite GUI number and every Native JSON number. Native `u64` values beyond JavaScript's safe-integer range and negative zero can therefore differ from what a person reviews after JavaScript conversion/stringification. This is a candidate defect, not evidence of a deployed-product incident. Apply `LANG-NUMERIC-002` as a draft rule here because the confirmed boundary crosses Native JSON numbers and JavaScript Number; no broader validation status is implied.

| Case | Oracle and public boundary |
|---|---|
| MTA-N01 | Native parses the original `9007199254740993` as an exact `u64`, then marks the pending request unavailable and rejects its response before a GUI conversion or transport write. |
| MTA-N02 | Native `u64`/`i64` values at both safe boundaries are accepted; either adjacent value outside the interval and the integer type extrema are rejected. |
| MTA-N03 | Finite floats within the interval, ordinary zero and positive/negative fractions remain supported. Large finite floats and both `-0` and `-0.0` are rejected. |
| MTA-N04 | Each real GUI component blocks both out-of-range directions, a large finite float and negative zero; safe boundaries, zero and finite fractions retain explicit one-time acceptance. The Native availability flag remains required. |

The numeric safety ceiling is finite, absolute value at most `Number.MAX_SAFE_INTEGER` (`9007199254740991`), and not negative zero. Native examines the original `serde_json::Number` through its integer/float representations; GUI checks happen before `JSON.stringify`. Nested objects and arrays use the same rule. This ceiling preserves the requested finite fractional-number behavior; it does not promise preservation of every decimal spelling or JSON numeric lexeme. Existing review byte/depth/detail limits, ownership, exact responses and persistence rejection remain unchanged.
